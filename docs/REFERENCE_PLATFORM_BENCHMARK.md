# مرجع المنصات المشابهة ومقارنة Maw3ed

**تاريخ البحث:** 2026-10-25  
**الغرض:** استخدام خصائص منشورة رسمياً من منصات جدولة/حجز ناضجة كمرجع لفئات المنتج، لا كترتيب تجاري أو ادعاء بأن تصميمها الداخلي معروف. الخصائص والأسعار تتغير؛ الروابط أدناه هي مصدر الادعاء المنشور.

## 1. أنماط مرجعية

### Calendly — جدولة الاجتماعات وتوجيه الطلب

التركيز المرجعي: تحديد أوقات متاحة مع مراعاة تقويم المستخدم، تقليل تبادل الرسائل، توجيه العملاء إلى الفريق المناسب، وإرسال إشعارات عند الحجز أو التغيير أو الإلغاء. صفحة المساعدة الرسمية تذكر تحديث تقويم المشاركين وإشعارات البريد للحجز وإعادة الجدولة والإلغاء، كما تذكر توجيه العملاء إلى أعضاء الفريق بحسب حاجتهم. [Calendly Scheduling FAQ](https://calendly.com/help/scheduling-faq)

**ما يفيد Maw3ed:** اتصال واضح بين availability والتقويم الحقيقي، وتأكيد/تغيير متزامن للطرفين، ومبدأ التوجيه عند وجود عدة مقدمين.

**حد المقارنة:** Calendly مرجع جدولة عام؛ لا يُفترض منه اكتمال متطلبات ملفات المرضى أو سير الزيارة الطبية.

### SimplyBook.me — حجز خدمات بفرق ومواقع

التركيز المرجعي: مقدمون بخطط شخصية وإجازات، إسناد الخدمة إلى مقدم، خيار “أي مقدم متاح”، مواقع متعددة، موافقة إدارية على الحجز، رسائل، إيداع/دفع، إلغاء وإعادة جدولة، مزامنة تقويم، تطبيقات إدارة/عميل. هذه أمثلة واردة في صفحات المنتج والأسئلة الرسمية. [SimplyBook.me Features](https://simplybook.me/en/booking-system-features) · [SimplyBook.me FAQ](https://simplybook.me/en/faq) · [SimplyBook.me product overview](https://simplybook.me/en/)

**ما يفيد Maw3ed:** المقارنة الأقرب لنظام إدارة خدمات، وتوضح أن “حساب الوقت المتاح” جزء فقط من منتج جاهز: الجداول الفردية، الموافقات، حالات الحجز، تذكير العميل، الدفع، إلغاء/تغيير، ونظام الفريق أجزاء مترابطة.

### مرجع SaaS متعدد المنشآت (نمط تصميم، لا منتج واحد)

لمنصة تعرض مساحة عمل وخططاً ومشغلين متعددين، المعيار العملي هو tenant context موثوق من جلسة المستخدم وعضويته، صلاحيات دورية على الخادم، حدود اشتراك قابلة للتتبع، وسجل نشاط إداري. لا تعني واجهة Super Admin أو وجود عمود `workspace_id` تحقيق هذه المتطلبات تلقائياً.

## 2. مصفوفة مقارنة القدرات

| القدرة | ما تعكسه المنصات المرجعية | وضع Maw3ed الحالي بحسب الكود/الوثائق | الفجوة/القرار |
|---|---|---|---|
| إظهار الأوقات المتاحة | جدولة مرتبطة بتقويم/توفر الفريق | ساعات وموظفون وخدمة ومدد وholds حسب الوثائق والكود | إثبات التزامن والمنطقة الزمنية وDST قبل الإنتاج |
| اختيار “أي مقدم متاح” | موجود كخيار في منصات الخدمات | موصوف في صفحة الحجز | اختبار التوزيع العادل وتعارض عدة موارد |
| ساعات مقدم الخدمة وإجازاته | جداول شخصية وإجازات/عطل | بعض ساعات الموظف؛ الوثائق تذكر الاستثناءات المتقدمة كنواقص | إضافة إجازات فردية واستثناءات متكررة إن كانت ضمن MVP |
| موقع/منشأة متعددة الفروع | دعم مواقع وربط مقدمين وخدمات بالموقع | نموذج مساحة وبيانات مؤسسة؛ لا يثبت تدفق تعدد المواقع | تحديد إن كان متعدد المواقع هدف الإصدار أو خارج النطاق |
| موافقة/تأكيد الحجز | حالات طلب وقبول/رفض وإشعارات | pending/confirmed في النواة؛ السياسة التفصيلية غير محسومة | state machine وصلاحيات وانتقالات وإشعار موثق |
| تغيير/إلغاء العميل | مسار ذاتي مع إشعار | روابط ذاتية مؤجلة وفق الوثائق | أولوية عالية لتقليل عبء الدعم؛ رموز توقيع قصيرة العمر |
| تذكير ورسائل متعددة القنوات | بريد وSMS/قنوات أخرى قابلة للإعداد | بريد موصوف، SMS/WhatsApp لاحق؛ وضع مزود البريد متضارب | تحديد مزود إنتاج، outbox/retries/consent/opt-out |
| دفع العربون | خيارات إيداع/دفع في رحلة الحجز | checkout غير مفعل، والجداول لا تعني قبول دفعة | عدم الإعلان عن دفع؛ تنفيذ webhooks وإعادة التسوية لاحقاً |
| مزامنة التقويم | تقويم خارجي يمنع التعارض ويحدث الطرفين | integration schema فقط وفق ما يظهر؛ التزامن غير مؤكد | لا تعرض كشغالة؛ تصميم OAuth/scopes/conflict policy |
| إدارة الفريق والأدوار | فريق يحدد من يفعل ماذا | membership roles في DB؛ ops endpoints غير محمية | **مانع إطلاق:** تنفيذ RBAC خادمي قبل تجربة مستخدم حقيقية |
| إحصاءات وتقارير | تقارير أداء الفريق والحجوزات | dashboard/stats أساسية | تعريف دلالات البيانات والمنطقة الزمنية والتصفية وpagination |
| تطبيق هاتف | تطبيق إدارة/عميل أو تجربة متكاملة | Expo WebView shell | وصفه كغلاف ويب فقط إلى أن توجد وظائف أصلية مختبرة |
| SaaS admin/billing | إدارة خطة وفوترة وإشعارات | لوحة منصة وسجل مالي وتفعيل يدوي | checkout 410؛ يلزم دورة حياة اشتراك كاملة أو إعلان واضح عن اليدوي |
| أمن المستأجر | وصول بالهوية والعضوية والدور | معرف المستأجر من header في `/api/ops`; لا مصادقة، ولا RLS | **مانع إطلاق:** مصادقة + tenant resolution + سياسة وصول fail-closed |
| تحمل التوسع | بيانات مركزية/قيود/تشغيل متعدد workers | JSON/ذاكرة مع مزامنة PG جزئية | نقل المصدر إلى PostgreSQL، قفل/قيود، ومحدد معدل موزع |

## 3. توصية نطاق المنتج

### MVP آمن لتجربة محدودة

- تسجيل دخول المالك وإدارة فريقه بأدوار حقيقية في API.
- خدمات ومقدمون وجدول أسبوعي وإجازات فردية أساسية.
- صفحة حجز، تأكيد يدوي/آلي حسب سياسة المنشأة، حماية التزامن، رسالة بريد واحدة موثوقة.
- تقويم استقبال ومعلومات عميل أساسية، دون بيانات طبية سريرية حساسة ما لم يوجد تصميم خصوصية/امتثال ملائم للسوق.
- اشتراكات يدوية معلنة بوضوح إن بقي checkout مغلقاً.
- إدارة backups ومراقبة وحوادث قبل استقبال عملاء فعليين.

### المرحلة التالية بعد ثبات النواة

- إلغاء/إعادة جدولة ذاتية، SMS/WhatsApp تذكير بموافقات واضحة.
- دفع عربون بعد تهيئة webhooks والتعامل مع النزاعات والاسترداد.
- تقويم خارجي ومواقع متعددة وقائمة انتظار، إن أثبتت مقابلات العملاء الحاجة.
- تطبيقات أصلية بعد قياس أن WebView لا يلبي الاستخدام الميداني.

## 4. الفروق التي لا يجوز طمسها في التسويق

- “وجود جداول الدفع” لا يعني أن الدفع الإلكتروني موصول.
- “وجود memberships” لا يعني أن كل `/api/ops` محمي بعضوية.
- “وجود holds” لا يضمن منع تداخل الحجز ذرّياً.
- “تعدد ملفات JSON حسب workspace” لا يثبت عزلاً أو قابلية تشغيل عدة workers.
- “واجهة منصة إدارية بأدوار” لا تعني RBAC لموظفي المنشآت.
- “مزامنة إلى PostgreSQL” لجزء من الحجز لا تجعل PostgreSQL مصدر الحقيقة لكل بيانات التشغيل.

## 5. مراجع أمنية ومعمارية لبناء معيار المقارنة

- OWASP API Security Top 10: مخاطر التفويض على الكائنات والوظائف والموارد وسير العمل: [API Security Top 10 2023](https://api-security.owasp.org/editions/2023/en/0x11-t10/).
- OWASP ASVS 5.0.0: متطلبات تحقق تقنية لتطبيقات الويب والخدمات: [ASVS](https://asvs.owasp.org/).
- Clerk: تحقق من جلسة كل طلب؛ بعد التحقق من الهوية لا يزال على التطبيق تحديد صلاحية المستخدم لهذا المورد: [Manual JWT verification](https://clerk.com/docs/guides/sessions/manual-jwt-verification).
- PostgreSQL RLS: سياسة صفوف يمكنها تقييد القراءة والكتابة لكل مستخدم؛ مع التفعيل وعدم وجود سياسة يكون السلوك الافتراضي رفض الصفوف، مع مراعاة أدوار تجاوز RLS: [Row Security Policies](https://www.postgresql.org/docs/current/ddl-rowsecurity.html).

## 6. طريقة قراءة الجدول

“موجود” يعني أنه مذكور في الوثائق أو له بنية/مسار في المستودع، وليس أنه مرّ باختبار قبول أو تم تشغيله في الإنتاج. “غير مؤكد” يعني أن الفحص الساكن لم يقدم دليلاً كافياً؛ لا أحوله إلى نفي قاطع ولا إلى ادعاء جاهزية.
