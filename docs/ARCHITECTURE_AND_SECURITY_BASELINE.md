# العمارة المستهدفة وخط أساس الأمان والتشغيل — Maw3ed

## 1. الحالة الحالية من قراءة المستودع

```text
React/Vite + صفحات HTML ──> Node.js HTTP server (server.js)
                                  ├── /api/admin/* : Clerk + platform roles
                                  ├── /api/ops/*   : workspace ID من العميل؛ مساحات DB عبر workspaceOpsPg، مع JSON/legacy fallback
                                  ├── /api/* قديمة : بعض المسارات تعتمد على معرف workspace الاختياري
                                  └── ملفات static / uploads

opsStore/opsWorkspace ──> API مجال موحدة + JSON fallback/cache
workspaceOpsPg         ──> تحميل/حفظ مطبع داخل transaction لمساحات workspace في DB
opsPg                  ──> مسار توافق أقدم للحجز مع organization/booking_pages
```

الخادم يستخدم `http.createServer` ومسارات يدوية؛ لا تظهر طبقة middleware مركزية تجمع المصادقة، التفويض، الرصد، وحدود الموارد. migration 010 و`workspaceOpsPg` يوفّران تخزيناً مطبعاً لمساحات workspace المسجلة في PostgreSQL داخل معاملة وقفل advisory لكل workspace، بينما تستمر مسارات محلية وlegacy وتبقى نسخة JSON مساعدة. `saveStore` يعيد بناء snapshot واسعاً لكل workspace؛ يلزم تدقيق مسارات القراءة/الكتابة والأداء قبل اعتباره مساراً إنتاجياً نهائياً. كما أن schema الحالي لا يتضمن سعة جلسات جماعية أو موارد قابلة للحجز.

## 2. العمارة الهدفية المقترحة

```text
Browser / mobile web
        │ HTTPS
Reverse proxy / TLS / trusted client IP
        │
Node API: request-id → parse/validate → Clerk authenticate → resolve tenant membership
        │                                   │
        ├── public booking policy           └── RBAC + audit
        ├── appointment domain service
        ├── transactional outbox
        └── rate limits / idempotency
                 │
PostgreSQL: tenant-owned data + constraints + transactions (+ RLS defense in depth)
        ├── job/outbox worker → email/SMS/payment/calendar providers
        ├── backups + tested restore
        └── metrics/logs/traces + alerting
```

يفضل إبقاءها modular monolith حتى تستقر حدود المجال. الأولوية لطبقات موحدة واختبارات عقد/صلاحيات، لا لتفكيك خدمات موزعة قبل ثبات مصدر البيانات.

## 3. قواعد الثقة ومسارات التفويض

1. **هوية:** يتحقق الخادم من رمز Clerk وتوقيعه وتوقيته وفق إعدادات المشروع. الهوية المستخرجة من الرمز هي المصدر الوحيد للمستخدم.
2. **المستأجر:** يرسل العميل workspace مختاراً لأغراض تحديد السياق فقط؛ يجب أن يتحقق الخادم من عضوية المستخدم الفعلية وحالة العضوية ومساحة العمل. لا تُقبل قيمة `x-workspace-id` كإذن.
3. **الفعل:** RBAC يقرر الفعل المحدد (قراءة مريض/تغيير سعر/إدارة موظف/إلغاء موعد). افتراض الرفض عند غياب دور/سياسة.
4. **الكائن:** كل استعلام وتحديث يربط الكائن بمستأجر محقق، ويعيد 404/403 دون تسريب بيانات مستأجر آخر.
5. **الحجز العام:** مسارات public محدودة لعرض معلومات صفحة منشأة عامة وإنشاء/عرض موعد بإثبات حامل رمز. لا تكشف قائمة المرضى أو إعدادات الإشعارات الداخلية.
6. **المنصة:** دور المنصة مستقل عن دور المنشأة؛ دعم/مالية/إدارة عليا بصلاحيات مفصولة وتدقيق، مع منع دعم المنصة من الاطلاع على بيانات سريرية دون إجراء طوارئ معتمد.
7. **الخدمات الخارجية:** توقيع webhooks، تحديد مصدر IP/توقيع عند دعم الموفر، idempotency، تحقق من schema، مهلة ومحاولات محدودة.

## 4. نموذج بيانات وعزل مستأجرين

- توحيد كل كيان تشغيلي تحت `workspace_id` أو `organization_id` ثابت؛ اختيار مصطلح واحد وحدود واضحة بين الاثنين.
- استخدام قيود مرجعية مركبة، مثلاً الموعد يشير إلى `(organization_id, patient_id)` و`(organization_id, doctor_id)`، حتى لا تنشأ علاقة بين كيانين من مستأجرين مختلفين.
- فصل بيانات الحساب عن بيانات المريض، وتقييد الحقول التي تظهر في الاستجابة حسب الدور.
- تفعيل PostgreSQL RLS بعد تصميم سياسة tenant context واختبار دور التطبيق الفعلي؛ لا تعتمد على RLS وحده إذا كان اتصال التطبيق بدور مالك/متجاوز للسياسات.
- عدم تخزين أسرار تكامل داخل `settings` العامة؛ استخدم مدير أسرار أو مخزناً مشفراً مع فصل المفاتيح.
- ترحيل ملفات JSON عبر إجراء idempotent، مقارنة أعداد/بصمات وتقرير تناقض، ثم قراءة فقط لفترة تحقق قبل إيقاف المصدر القديم.

## 5. الحجز والتزامن

1. احتساب فترة الإشغال `start_at` إلى `end_at + buffer` في UTC مع حفظ المنطقة الزمنية للمنشأة/المورد.
2. hold في PostgreSQL بحالة وانتهاء صلاحية مع مفتاح idempotency؛ ليس ملفاً أو Map داخل عملية.
3. إنشاء الموعد في معاملة واحدة: تحقق من الخدمة/الطاقم والحدود، تثبيت المورد/الفترة، كتابة الموعد، تحديث الحصة، كتابة outbox.
4. قيد قاعدة بيانات أو قفل منطقي يغطي تداخل الفترات، لا تطابق وقت البداية فقط.
5. إرسال التأكيد بعد commit من worker؛ لا تفشل عملية الحجز بسبب توقف البريد ولا تفقد الرسالة بصمت.
6. الإلغاء/التغيير والتحصيل أحداث حالة مؤرخة ومكررة بأمان؛ أي callback خارجي لا يكرر أثره.

## 6. خط الأساس الأمني المطلوب

| المجال | ضابط القبول |
| --- | --- |
| مصادقة | كل مسارات التشغيل والحساب تحميها جلسة صحيحة؛ العامة allowlist معلنة |
| تفويض | اختبارات لكل دور ولكل route/method وحالة كائن عابر لمستأجر |
| الجلسة/CSRF | سياسة cookie وSameSite وCSRF حسب الأصل؛ لا تسجيل tokens |
| الإدخال | schema validation لكل payload، حدود body، أنواع وحقول مسموحة، أخطاء عامة للعميل |
| المعدل | limits مشتركة بين workers، مع IP موثوق من proxy + المستخدم/tenant ومسار العمل |
| الملفات | أسماء/امتدادات/حجم/MIME مفحوصة، منع traversal، ملفات خاصة لا تخدم للعامة |
| HTTP | TLS، HSTS، CSP، nosniff، frame policy، referrer policy، CORS محدود؛ مراجعة Nginx |
| الأسرار | خارج Git والـ logs، تبديل بعد الاشتباه، صلاحيات أقل، فصل production عن development |
| البيانات | تشفير النقل والقرص والنسخ، احتفاظ وحذف وتصدير، عدم استخدام بيانات حقيقية في demo |
| التدقيق | عمليات إدارية/مالية وتغيير الصلاحية/الحالة لها سجل actor/tenant/action/result |
| التبعيات | lockfile واحد، تثبيت نسخ، فحص اعتماديات في CI، تحديث منتظم تحت مراجعة |

استخدم [OWASP ASVS](https://asvs.owasp.org/) كقائمة تحقق و[OWASP API Security Top 10](https://api-security.owasp.org/editions/2023/en/0x11-t10/) لتصنيف مخاطر API.

## 7. التشغيل والنشر

- أوضاع التطبيق المعتمدة حالياً `local` و`production`؛ `npm run check:staging` فحص قبول production-like معزول وليس وضع تشغيل ثالثاً. أي بيئة staging دائمة تحتاج قراراً مستقلاً وتحديث [ENVIRONMENTS.md](ENVIRONMENTS.md).
- حسم Node.js LTS ومدير حزم/lockfile واحد بقرار موثق؛ توجد lockfiles متعددة حالياً. بعد الحسم، يثبت CI الاعتماديات بالطريقة المطابقة، ويبني الواجهة والخادم، ويشغل migrations على قاعدة مؤقتة واختبارات API.
- migrations تقدمية وقابلة للتراجع أو forward-fix، مع لقطة احتياطية قبل تغيير مخطط خطر.
- health/readiness يميز أن العملية حية من جاهزية قاعدة البيانات والمهاجرات ومزود الرسائل.
- reverse proxy يثق بعناوين forwarded من proxy واحد معروف ولا يقبل تزويرها من الإنترنت.
- structured logs مع request ID وtenant ID منقح، زمن/نتيجة، دون بيانات صحية أو رمز جلسة.
- تنبيهات لفشل DB/المهاجرات/outbox/backup، ارتفاع 4xx/5xx، التأخير، امتلاء القرص، ومحاولات دخول غير طبيعية.
- backup مشفر خارج المضيف، سياسة احتفاظ واضحة، استعادة دورية على بيئة معزولة، تسجيل نتيجة الاستعادة.
- وثيقة rollback تحدد commit/image السابق، مخطط التوافق، وإجراء إيقاف الرسائل/الحجوزات عند الحاجة.

## 8. بوابات قبول قبل الإطلاق

### بوابة الأمن

- 401 دون جلسة على كل مسارات التشغيل الخاصة.
- 403 أو 404 آمن لمستخدم ليس عضواً، حتى مع تبديل `workspace` وIDs.
- كل دور يقرأ/يغير ما هو مسموح فقط؛ تغيير حقل محمي/زيادة صلاحية مرفوض.
- لا بيانات مرضى في سجل التطوير العام أو ملفات static.
- اختبارات injection، CSRF/CORS حسب السياق، rate limit، payload limits، واستكشاف endpoint inventory.

### بوابة البيانات

- حجزان متزامنان لنفس المورد/أوقات متداخلة: واحد فقط ينجح.
- كل العلاقات الداخلية تنتمي إلى المستأجر نفسه.
- نسخة احتياطية تستعاد وتنتج أعداداً/بصمات متوافقة.
- ترحيل JSON إلى PostgreSQL ينتهي بلا سجلات يتيمة أو اختلافات غير مفسرة.

### بوابة التشغيل

- تثبيت نظيف من lockfile على بيئة مماثلة للإنتاج، migrate/build/start/restart.
- readiness يعكس تعطل dependencies، مع تنبيه واضح.
- اختبار بريد/رسائل sandbox وعدم تكرار الإرسال بعد retry.
- خطة rollback ومالك مناوبة وتصعيد للحادث موثقة.

هذه بوابات مواصفة مستهدفة، وليست نتائج تنفيذ. الحالة الحالية مفصلة في [تقرير الجاهزية](PRODUCTION_READINESS_REPORT.md).
