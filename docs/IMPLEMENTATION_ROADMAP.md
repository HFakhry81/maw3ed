# خارطة تنفيذ Maw3ed الموحدة: من إغلاق المخاطر إلى إطلاق المجالات

**تاريخ المراجعة:** 2026-10-27
**الأساس:** [تقرير الجاهزية](PRODUCTION_READINESS_REPORT.md)، [مواصفات المنتج](PRODUCT_AND_PLATFORM_SPEC.md)، [مقارنة المنصات](REFERENCE_PLATFORM_BENCHMARK.md)، [خط أساس العمارة والأمان](ARCHITECTURE_AND_SECURITY_BASELINE.md)، و[نموذج السعة والتعليم والأنشطة](WORKSPACE_CAPACITY_MODEL_EDUCATION_AND_VERTICALS.md).  
**نوع الوثيقة:** خطة تنفيذ مستهدفة وليست إثباتاً بأن الميزات أو الضوابط نُفذت. آخر تقارير الجاهزية المذكورة مبنية على فحص ساكن؛ يجب إعادة فحص الكود وتشغيل الاختبارات عند بدء كل دفعة.  
**قاعدة الإطلاق:** لا إطلاق عام متعدد المنشآت ولا استخدام بيانات مرضى/طلاب حقيقية قبل اجتياز بوابات الهوية والعزل والخصوصية والتزامن والاستعادة والتشغيل.

## النتيجة المطلوبة

تحويل النواة الحالية إلى منصة خدمات متعددة المنشآت قابلة للاختبار والإطلاق المتدرج، مع الحفاظ على بنية modular monolith وتطويرها دون تفكيك مبكر إلى خدمات موزعة. المطلوب:

1. تفويض خادمي كامل لكل مستأجر ودور.
2. مصدر حقيقة واحد لكل مساحة عمل: PostgreSQL لمساحات الإنتاج بعد قبول الترحيل، مع الحفاظ على مسار JSON المحلي المدعوم؛ وحجز ذري لا يسمح بالتداخل.
3. نواة حجز مشتركة، وسياسات صريحة للخدمة/المورد، ثم تفعيل المجالات وفق أولوية واضحة.
4. رحلات عميل وتشغيل ومنصة معلنة الحالة؛ لا تعرض ميزة غير موصولة على أنها جاهزة.
5. اختبارات قابلة لإعادة التشغيل، وقبول معزول بإعداد production-like، ونشر قابل للرصد والاستعادة والرجوع.

## نموذج المجال المستهدف

القالب يهيئ المصطلحات والبيانات الأولية؛ لا يحدد وحده آلية الحجز أو السعة. افصل بُعدين في النموذج: `occupancy_mode` يحدد ما الذي يشغله الحجز، و`composition` يحدد هل هو خدمة واحدة أم حزمة بنود. يجب أن تدعم النواة سياسات إشغال معلنة على الخدمة/الجلسة/المورد:

- **`exclusive`:** فترة لمقدم أو مورد واحد؛ تمنع التعارض على كل مورد مطلوب.
- **`session_capacity`:** جلسة occurrence مشتركة بسعة محددة وتسجيلات/حضور متعددة؛ التسجيل المتزامن لا يتجاوز السعة.
- **`rental`:** حجز مورد لفترة، مع سياسة محددة لسعة المستخدمين المصاحبين عند الحاجة.
- **تركيب الحجز:** `single` أو `bundle`؛ الـ bundle booking رئيسي واحد يضم `booking items` متعددة. لكل بند `occupancy_mode` مستقل وفترة وسعر ومقدم/مورد عند الحاجة. التركيب ليس نمط إشغال رابعاً.

يمكن لأي نشاط استخدام أكثر من نمط. لا تستنتج السياسة من `activity_mode` ولا تعلن دعم جلسات تعليمية جماعية لمجرد وجود قالب `education`.

## مرجعية القرار

عند التعارض، اتبع الترتيب التالي ولا تستنتج الجاهزية من وجود شاشة أو جدول فقط:

1. الكود الحالي والاختبارات التي شُغّلت فعلياً يثبتان السلوك المنفذ.
2. [تقرير الجاهزية](PRODUCTION_READINESS_REPORT.md) يحدد المخاطر المفتوحة، ويجب تحديث نتائجه عند إعادة الفحص.
3. [خط الأساس المعماري والأمني](ARCHITECTURE_AND_SECURITY_BASELINE.md) يحدد الضوابط الهدفية.
4. [مواصفات المنتج](PRODUCT_AND_PLATFORM_SPEC.md) تحدد النطاق والرحلات المستهدفة.
5. [نموذج السعة والأنشطة](WORKSPACE_CAPACITY_MODEL_EDUCATION_AND_VERTICALS.md) يحدد امتدادات التعليم والموارد والحجز الجماعي.
6. [مقارنة المنصات](REFERENCE_PLATFORM_BENCHMARK.md) مرجع لقدرات معلنة علناً، وليست إثباتاً لتصميم داخلي أو تكافؤ Maw3ed معها.

الأوضاع الرسمية للتطبيق هي `local` و`production` فقط. `npm run check:staging` هو فحص قبول قبل الإطلاق بإعداد production-like معزول، وليس وضعاً ثالثاً أو بيئة staging دائمة. راجع [ENVIRONMENTS.md](ENVIRONMENTS.md) قبل تغيير هذا القرار.

## نموذج التنفيذ والحوكمة

- أنجز كل مرحلة في تغييرات صغيرة قابلة للمراجعة. لا تعتبر الوثائق أو وجود endpoint أو migration دليلاً على الإنجاز دون اختبار ناجح.
- قبل البدء، سجل رقم المرحلة، نطاقها، المالك، المتطلبات السابقة، ملفات/مخرجات التغيير، الاختبارات، وخطة rollback أو forward-fix.
- لا تنتقل إلى مرحلة تعتمد على بوابة فاشلة. يمكن تنفيذ أعمال توثيق مستقلة بالتوازي، لكن لا يمكنها تجاوز بوابة أمن أو بيانات.
- عند الانقطاع، استأنف من آخر مرحلة ذات دليل قبول محفوظ، لا من الحالة المكتوبة كـ “تم” فقط.
- لا تشغّل `npm run update:all` أو مسارات refresh/backend الواسعة كفحص روتيني؛ قد تنفذ migrate/seed/reset/restore. راجع [refresh-and-test.md](refresh-and-test.md)، وخذ نسخة احتياطية قبل أي مسار قد يغيّر بيانات تشغيل.
- فحص ما قبل الإطلاق المعتمد حالياً هو `npm run check:staging` بإعداد production-like معزول؛ لا تنشئ وضع تطبيق أو أسراراً باسم `staging` دون قرار معماري منفصل.

## المرحلة 0 — حصر المسارات وخفض التعرض

### قرارات المنتج قبل التنفيذ

- حدد الإصدار/المجالات التي ستُطلق أولاً، ومن المستخدمين المقصودين لكل مجال، وما سيظل مخفياً أو تجريبياً.
- احسم سياسة تأكيد الموعد والإلغاء وإعادة الجدولة والعربون/الاسترداد، العملة والمنطقة الزمنية، وحدود الحجز والمهلة الزمنية.
- احسم أدوار المنشأة وصلاحيات كل إجراء، فصل حساب المستخدم عن ملف الموظف، ومسار إنشاء أول مسؤول منصة.
- للتعليم/الأنشطة الجماعية: حدد تسجيل الطالب في مقرر/مجموعة أم occurrence، ولي الأمر/المستفيد، قواعد المقاعد، وسعة القاعة الفعلية. لا تُملأ هذه القيم بالاستنتاج من الملف المرفق.
- احسم سياسة قالب النشاط عند إنشاء مساحة العمل: اختيار قالب جاهز أو قالب فارغ، ثم قفل غير قابل للتغيير من واجهة المنشأة؛ أي استثناء إداري لاحق يجب أن يكون محدوداً ومؤكداً ومدققاً.
- حدد تصنيف البيانات وفترات الاحتفاظ والحذف والتصدير والموافقة على الرسائل، مع مراجعة قانونية حسب أسواق الإطلاق؛ لا تفترض انطباق HIPAA أو GDPR تلقائياً.
- سجل لكل قرار مالكاً وتاريخاً وحالةً (محسوم/معلّق) وتأثيراً في المخطط وواجهة المستخدم والاختبارات.

### مهام المرحلة

- جرد كل المسارات من `server.js` و`opsRoutes.js` و`platformAdminRoutes.js` حسب HTTP method، مع تصنيفها إلى: عامة، مستخدم مسجل، عضو منشأة، مسؤول منصة، داخلية/محذوفة.
- إيقاف أو حماية عاجلة لـ`/api/ops/*`؛ إذ تقبل مساحة عمل من `x-workspace-id` أو query parameter ولا تتحقق حالياً من عضوية المستخدم.
- إيقاف/حماية الواجهات القديمة `/api/patients`, `/api/appointments`, `/api/dashboard` حتى لا تعتبر مساراتها القديمة استثناءً من سياسة الصلاحيات.
- إيقاف `GET/POST /api/development-events` في الإنتاج أو تقييده بمسؤول مصادق عليه، وإضافة تدوير واحتفاظ للسجل.
- تعطيل التسجيل التلقائي لـ`super_admin` لأول مستخدم في بيئة الإنتاج؛ استبداله بإجراء bootstrap أحادي الاستخدام، موثق، مؤقت ومدقق.
- إعداد بيانات اصطناعية فقط للاختبار، ومنع نسخ بيانات الإنتاج إلى local أو قبول ما قبل الإطلاق دون إخفاء هوية معتمد.

### معيار الخروج

- لكل مسار مالك ونوع وصول معروف.
- كل متطلب منتج له قرار أو سؤال معلّق بمالك؛ لا تبدأ migration مبنية على افتراض مجال غير معتمد.
- جميع المسارات الخاصة ترد `401` دون جلسة، والمسارات العامة تكشف حقولاً مسموحة فقط.
- لا يعود أي endpoint قديم نافذة التفاف حول auth الجديد.

## المرحلة 1 — المصادقة، ملكية المساحة، وRBAC

### مهام تنفيذ التفويض

- بناء طبقة مشتركة في الخادم: التحقق من Clerk → استخراج user id → حل workspace من عضوية قاعدة البيانات → التحقق من حالة المستخدم/المساحة → فحص الإذن للعملية.
- اعتبار `x-workspace-id` مجرد اختيار سياق؛ التحقق من membership لكل طلب. يمنع تماماً استخدامه كدليل تفويض.
- تحديد مصفوفة أدوار API: `owner`, `admin`, `manager`, `staff`, `viewer` مع صلاحية مستقلة للتقويم، العملاء، إعدادات الحجز، الأسعار، المصروفات، المستخدمين، والتصدير.
- استبدال صلاحيات الواجهة/localStorage بتفويض على الخادم، مع تقليل الحقول المسموحة لكل دور.
- مراجعة `requireAppUser` ومنطق أول مستخدم، وإجراء bootstrap آمن لدور مالك المنصة دون سباق تسجيل متزامن.
- حماية `/api/ops/*` وكل المسارات القديمة، بما فيها القراءة والإنشاء والتعديل والحذف وعمليات desk.
- منع BOLA: استعلامات وتعديلات appointments/customers/staff/services مشروطة بالمنظمة المحققة، مع عدم كشف وجود كائن في مستأجر آخر.
- توحيد الأخطاء: `401` للهوية الغائبة، `403` للدور غير الكافي، و`404` آمن للكائن العابر للمنشأة؛ لا ترجع stack أو أخطاء قاعدة البيانات.

### اختبارات قبول الهوية والتفويض

- دون جلسة: كل مسارات ops والإدارة القديمة ترفض.
- عضو منشأة A يغير workspace ID إلى B: لا قراءة ولا تعديل ولا تمييز يكشف بيانات B.
- كل دور يمر فقط بالأفعال المسموحة؛ التحقق يشمل التعديل المباشر عبر API، وليس القوائم المخفية فقط.
- user معلق أو workspace موقوف لا ينفذ عمليات تشغيل.
- لا يستطيع مستخدم عادي ترقية نفسه أو تعيين platform role أو استغلال التسجيل المتزامن للحصول على `super_admin`.

## المرحلة 2 — PostgreSQL مصدر الحقيقة وسلامة الحجز

### العمل

- اعتماد `workspace_id` كحد بيانات تشغيلي بعد توثيق علاقته بـ`organization_id` في المسارات القديمة؛ إضافة مفاتيح مركبة تمنع الربط العابر للمساحات.
- migration 010 و`workspaceOpsPg` يقدمان تخزيناً مطبعاً لبعض مساحات PostgreSQL، لا دليلاً على تغطية كل نوع workspace. جرد كل كيان ومسار في PostgreSQL وJSON/legacy قبل اختيار خطة الترحيل؛ حافظ على fallback المحلي ما دام مدعوماً ومطلوباً.
- نقل أي بيانات تشغيلية وholds ما زالت تعتمد على JSON/المسارات القديمة، أو توثيق سبب بقائها مؤقتاً، وتحديد الجداول والقيود والفهارس وrollback/forward-fix.
- بناء أداة ترحيل قابلة لإعادة التشغيل: dry-run أولاً، نسخة احتياطية، تقرير فروق بالأعداد والمعرفات والعلاقات والـ slugs، ثم كتابة/تحقق ونافذة قراءة فقط قبل التحويل. لا تمسح المصدر قبل قبول المالك.
- قياس مسار `saveStore` الذي يعيد بناء snapshot workspace داخل transaction، ثم الانتقال إلى تحديثات دقيقة عند الحاجة. بعد إثبات مصدر الحقيقة، إيقاف الكتابة التشغيلية إلى JSON والإبقاء على أي cache/backup بحدود موثقة فقط.
- نقل rate limits والـ holds إلى خدمة مشتركة/قاعدة بيانات بحيث تعمل عبر workers، وتوثيق سياسة proxy الموثوق لعناوين العميل.
- تحديد timeout، ترتيب الأقفال، مستوى العزل، retry للأخطاء القابلة لإعادة المحاولة، وقيد/استراتيجية منع التداخل؛ لا تعتمد على `SELECT FOR UPDATE` لصف غير موجود.
- لا تفعّل RLS إلا مع سياق tenant موثوق ودور تطبيق لا يتجاوز السياسات واختبارات عدم التسرب؛ وإلا وثق الضوابط التعويضية وخطرها المتبقي.

### اختبارات قبول البيانات والحجز

- طلبان متزامنان للفترة/المورد نفسه: نجاح واحد فقط، والآخر تعارض معروف.
- فترتان متداخلتان جزئياً مع بدايتين مختلفتين: لا يسمح بالتعارض.
- حساب التوفر والحجز النهائي يستخدمان timezone ومدة الخدمة والفاصل والاستثناءات نفسها.
- ترحيل مكرر آمن؛ لا ينشئ نسخاً أو slugs متضاربة، ويصدر تقريراً يمكن مراجعته.
- استعادة backup إلى بيئة معزولة تعيد الجداول والقيود والبيانات اللازمة لتشغيل الحجز.

## المرحلة 3 — نواة التوفر والحجز الذري

### تنفيذ محرك الحجز

- توحيد حساب availability والحجز النهائي للـ JSON المحلي وPostgreSQL، مع فترة واضحة `[start, end + buffer)` والمنطقة الزمنية وقواعد DST.
- إتمام الحجز داخل معاملة/قفل موثوق: تحقق tenant والخدمة والمقدم والمورد والسعة، تثبيت hold، كتابة الحجز/المقاعد، وتسجيل التدقيق وoutbox؛ لا يرسل إشعاراً قبل commit.
- تصميم الحجز idempotently؛ retry لنفس المفتاح لا ينشئ موعداً أو خصماً أو رسالة مكررة.
- جعل الإلغاء/انتهاء hold يحرر الفترة أو المقاعد مرة واحدة، وتحديد statuses التي تشغل المورد/السعة.
- اعتماد قيود DB أو آلية قفل صحيحة تمنع تداخل الفترات فعلياً؛ قيد الوقت المتساوي وحده غير كافٍ.

### اختبارات قبول النواة

- اختبار متزامن على نفس المورد وفترتين متداخلتين ببدايات مختلفة: نجاح واحد فقط؛ الفترة المتجاورة غير المتداخلة تنجح.
- اختبار retry متكرر، انتهاء hold، إلغاء، وتحرير المورد/المقعد مرة واحدة.
- تحقق أن slots المعروضة والحجز الفعلي يستخدمان قواعد المدة وbuffer والمنطقة الزمنية نفسها.
- اختبر هذه العقود على JSON المحلي ومساحة PostgreSQL، أو وثق صراحةً أي مسار مستثنى من الإصدار.

## المرحلة 4 — الموارد والسعة وامتدادات المجالات

### بناء الموارد والسعة

- إضافة موارد عامة (مثل غرفة، كرسي، جهاز، طاولة) بملكية tenant وسعة وحالة وموقع، ومتطلبات خدمة/تخصيص مورد لكل booking item أو occurrence.
- تنفيذ `exclusive` و`rental` وسياسة الحجز المركب قبل ادعاء الدعم؛ كل item يحمل الوقت والسعر والمقدم/المورد المطلوبين عند انطباقها.
- اعتمد سيناريو قبول مستقل لكل عمود رأسي: عيادة بموعد حصري، صالون بحجز خدمات مركب، بلياردو/معدات بحجز rental، لياقة بتدريب فردي وجلسة جماعية، وتعليم بمقاعد وحضور. لا يلزم إطلاق كل عمود رأسي في الإصدار الأول.
- للتعليم والرياضة الجماعية: إضافة series وoccurrences وcapacity وenrollments/attendees وattendance، مع composite foreign keys وحدود workspace.
- في التسجيل الجماعي: اقفل صف occurrence الموجود، أعد حساب المقاعد النشطة داخل المعاملة، امنع التسجيل المكرر، وأعد خطأ تعارض معروفاً عند الامتلاء.
- احتسب سعة التسجيل من قيود قابلة للمقارنة بوحدة المقعد: سعة occurrence، حد إشغال القاعة، ومقاعد/أجهزة مخصصة لكل مشارك. لا تعامل عدد الموارد كأنه عدد مقاعد إلا مع تعريف صريح للوحدة. افصل entitlement الخطة عن الحد المادي؛ ارفض الإعداد الأعلى أو اعرض سبب/حد السعة بوضوح، ولا تخفضه بصمت.
- افصل تأهيل المدرس للخدمة عن تخصيصه الفعلي لوقوع الجلسة؛ افصل ملف الطالب عن حساب ولي الأمر، واحسم سياسة enrollment للمقرر مقابل الجلسة قبل بناء الواجهة.

### بوابة قبول امتدادات المجال

- سعة 50: أول 50 مقعداً تنجح، والـ51 يرفض؛ ومع ثلاثة مقاعد متبقية وطلبات متزامنة كثيرة، لا ينجح أكثر من ثلاثة.
- لا يسجل المستفيد نفسه مرتين في occurrence وفق السياسة، والإلغاء يحرر المقعد مرة واحدة.
- لا يتداخل مدرس أو قاعة أو مورد حصري بين occurrences؛ قاعة سعتها 30 لا تقبل جلسة سعتها 50.
- booking مركب ذري: فشل مورد لأي item لا يترك حجزاً ناقصاً؛ كل item يحتفظ بمدته وتسعيره ومورده.
- اختبارات العزل تمنع قراءة/ربط طالب أو مورد أو تسجيل من workspace أخرى.

لا تُفعّل هذه المرحلة قالب `education` أو قالباً جماعياً في production قبل نجاح migrations والاختبارات أعلاه؛ القالب وحده لا ينشئ هذه الوظائف.

## المرحلة 5 — رحلات المنتج والواجهة

### 5.1 الحجز والتقويم

- توحيد state machine من طلب الموعد حتى الإلغاء/الاكتمال/no-show، وتحديد من يستطيع كل انتقال وسبب التغيير.
- دعم ساعات كل مقدم خدمة، إجازات فردية، استراحات متعددة، إغلاق متكرر، مواقع/موارد إذا كانت ضمن الإصدار المستهدف، والمنطقة الزمنية والتوقيت الصيفي.
- إكمال إلغاء/إعادة جدولة العميل برابط موقّع محدود العمر والاستعمال، مع إشعار وتسجيل الحدث.
- تحديد سياسة الموافقة: تأكيد فوري أو pending ثم اعتماد من الاستقبال، وإظهار حالة واضحة للعميل.
- ضمان أن رمز بطاقة الحضور لا يتيح بيانات زائدة، وأنه قابل للإبطال ومحدود المحاولات.

### 5.2 تشغيل المنشأة والبيانات

- إكمال RBAC على موظفي الاستقبال ومقدم الخدمة والمدير والمالك بما يتوافق مع الجدول السابق.
- إضافة pagination/filter/limits للقوائم، وتقليل بيانات المريض إلى ما يلزم لكل شاشة ودور.
- تعريف قيود الاشتراك/usage من `plan_catalog` واشتراك PostgreSQL، مع منع الاعتماد على حدود ذاكرة محلية وحدها.
- وضع سياسة retention، تصدير، حذف، تعديل بيانات العميل، وموافقة رسائل ترويجية منفصلة عن رسائل الخدمة.

### 5.3 التوثيق والواجهة

- اختيار القالب يتم ضمن إنشاء workspace، مع خيار فارغ واضح ورسالة تأكيد أن النوع سيقفل؛ يرفض الخادم تغيير `activityTemplateId` بعد القفل، ولا يكفي تعطيل عنصر الواجهة.
- لا يظهر اختيار/تبديل النشاط داخل لوحة المنشأة بعد الإنشاء. أي فك قفل استثنائي لمسؤول المنصة يجب أن يكون role-gated، تأكيداً ثنائياً، audit event، وسبباً مسجلاً.
- حافظ على سلامة الكتالوج في الخادم: منع تكرار اسم الخدمة والفئة والموظف ضمن النطاق المتفق عليه، وإرجاع خطأ مفهوم؛ اختبر create وupdate والاختلافات في المسافات/التطبيع.
- اعرض عدد الخدمات بجوار اسم الفئة، واحسبه من البيانات الحالية مع تضمين/استبعاد المتوقف حسب قرار المنتج الموثق.
- تصحيح README وتشغيل التطوير، فهرسة الوثائق، توحيد الأسماء بين booking/customer/patient وworkspace/organization.
- التمييز في واجهة المنتج بين ميزة جاهزة وميزة متوقفة؛ لا تعرض الدفع/المزامنة/التطبيق الأصلي كمتاح إن كان مجرد schema أو WebView.
- تطبيق RTL واللغة والعملة والمنطقة الزمنية على رحلة الحجز والإدارة كاملة؛ استهدف WCAG 2.2 AA، بما يشمل لوحة المفاتيح والتركيز وقارئ الشاشة وإشعارات الأخطاء، مع فحص آلي ومراجعة بشرية.

### معيار خروج رحلات المنتج

- سيناريوهات الرحلة من إعداد المنشأة حتى إغلاق الزيارة تعمل من UI وAPI وفق الأدوار.
- لكل تغيير حالة سجل actor/timestamp/source؛ الإشعارات لا تكرر أو تفقد عند إعادة المحاولة.
- واجهات العملاء لا تعرض سجلات أو حقولاً خارج غرضها.

## المرحلة 6 — الرسائل والدفع والتقويم والتكاملات

حدد مبكراً هل هذه ميزات شرط إطلاق أم مرحلة لاحقة. إن كانت ضمن المواصفة، تنفذ كاملة قبل تسويقها.

- أنشئ مصفوفة capability لكل مجال تقارن المتطلب بقدرات معلنة في المراجع الرسمية لـ Calendly وSimplyBook.me، ثم صنّف كل قدرة: ضمن MVP، مؤجلة، أو خارج النطاق. لا تستخدم المقارنة ادعاءً بالتكافؤ أو نسخاً لتصميم داخلي.

### الرسائل

- حسم مزود إنتاج واحد وقناة transactional واحدة أولاً؛ إزالة تناقضات إعداد Gmail/Replit وVPS قبل الاعتماد.
- transactional outbox، توقيع/مصادقة callback حسب المزود، retries بحد أقصى وbackoff، idempotency، وسجل تسليم منقح.
- فصل إشعارات الخدمة عن التسويق؛ موافقة/انسحاب وتفضيلات القناة وساعات الإرسال حسب السوق، وعدم تسجيل محتوى صحي أو بيانات طالب غير لازمة.
- حماية نقاط التحقق من البريد بمعدل لكل بريد/IP/جهاز، صلاحية واستخدام مرة واحدة، ورسائل عامة لا تكشف وجود حساب.

### الدفع والاشتراك

- إبقاء أي checkout معطل معلماً بوضوح حتى اكتمال المزود؛ لا تفعيل اشتراك بناءً على redirect متصفح.
- تنفيذ sandbox أولاً: تحقق توقيع webhook، idempotency، مبلغ وعملة ومرجع provider، فشل/إلغاء/استرداد، مطابقة دفتر الاشتراكات، وإشعار المستخدم.
- استخدم hosted checkout/tokenization من مزود معتمد، ولا تستقبل أو تخزن PAN/CVV في Maw3ed؛ حدد نطاق PCI مع المزود ومختص قبل أي تشغيل مدفوع.
- توثيق آلية التفعيل اليدوي كبديل تشغيلي مؤقت مع فصل موافقة الطالب عن منفذ التفعيل والتدقيق.

### التقويم الخارجي

- اعتماد scopes دنيا، OAuth tokens مشفرة، سياسة تعارض/مصدر الحقيقة، معالجة انتهاء token، وإعادة مزامنة بعد webhook/retry.
- اختبار الحجز في Maw3ed والحجز الخارجي المتزامنين وعدم إنشاء تكرارات عند إعادة الإرسال.
- أي تبادل بيانات صحية عبر HL7 FHIR نطاق اختياري مستقل: حدد use case، إصدار/ملف توافق، consent وauthorization وaudit mapping أولاً؛ لا تجعل FHIR شرطاً لنواة الحجز ولا تدّعِ توافقاً دون اختبار conformance.

### معيار خروج التكاملات

- اختبارات provider sandbox وتوقيع webhook والرسائل الفاشلة/retry ناجحة؛ أو تخفى الميزات غير المنفذة ويذكر نطاق الإصدار ذلك صراحة.

## المرحلة 7 — التشغيل والأمن والخصوصية

- حسم مدير الحزم وlockfile واحد بإجراء مراجعة واعتماد؛ المستودع يحتوي lockfiles متعددة حالياً، فلا تحذف/تولد lockfiles تلقائياً. ثبّت إصدار Node المتفق عليه في ملفات التشغيل وCI.
- فصل الأسرار والبيانات المحلية عن المستودع؛ تدقيق history والمخرجات دون طباعة قيم الأسرار، وتدوير ما يشتبه بتعرضه.
- مراجعة Nginx/TLS: proxy للداخل فقط، forwarded headers موثوقة، HSTS وCSP وnosniff وframe/referrer policy وCORS محدد.
- تحديد body/list limits، معدل طلب موحد، حماية auth/OTP/booking، والحد من التسجيل على القرص.
- عدم كشف رسائل exception للعميل؛ إضافة request ID وstructured logging منقح.
- إضافة readiness منفصل عن liveness، مراقبة DB وqueue/outbox/disk، تنبيهات، نسخة احتياطية مشفرة، سياسة احتفاظ، واختبار استعادة.
- توثيق تصنيف بيانات المريض، الوصول الإداري، طلبات الخصوصية والحذف، إدارة الحوادث، ومن يملك المفاتيح/التصعيد.
- مراجعة تبعيات المشروع وملفات upload ومسارات static على مسارات فعلية قبل إتاحة الإنتاج.
- حدد حدود الجسم والقوائم ومعدلات الطلب، ومنع spoofing لـ forwarded headers، ومفاتيح rate limit مشتركة عند تعدد workers.
- اعتمد RPO/RTO واحتفاظ backup ومدة الاستعادة مع مالك المنتج، ثم نفّذ restore drill موثقاً؛ لا تضع أرقام SLA من دون حمل وقرار معتمد.
- صنّف بيانات القاصرين/الطلاب والمرضى، وحدد صلاحيات ولي الأمر/الوصي، الطلبات القانونية للخصوصية، الإزالة والتصدير وسجل الوصول قبل تفعيل المجال.
- احفظ مصفوفة `route × method × role × object/property`؛ افصل سجل المنصة عن سجل tenant، وسجّل قراءة/تصدير البيانات الحساسة وسجل التدقيق، وراجع اكتمال الأحداث عالية الخطورة.

## المرحلة 8 — قبول ما قبل الإطلاق

### تكوين البيئة

- استخدم آلية `npm run check:staging` الحالية للتحقق production-like المعزول؛ هذا اسم فحص وليس mode جديداً في التطبيق.
- إذا احتاجت المؤسسة لاحقاً بيئة staging دائمة، فاعتمد قراراً منفصلاً يحدد المالك والتكلفة وClerk/DB/DNS/secret isolation ونسخ البيانات وعمليات التنظيف، ثم حدّث [ENVIRONMENTS.md](ENVIRONMENTS.md) قبل إضافتها.
- لا تستخدم `.env.production` أو بيانات حية في فحص القبول؛ كل secret منفصل وله مالك وتاريخ تدوير.
- نفذ الفحص على نفس build/revision وإصدارات Node/DB/migrations/proxy المتوقعة للإنتاج، ببيانات اصطناعية.

### بوابات CI المطلوبة

1. تثبيت نظيف من مدير الحزم وlockfile المعتمد وإصدار Node المثبت.
2. فحص تنسيق/تحليل ساكن وبناء frontend/backend. إذا لم يوجد script لهذه الفحوص، أضفه واعتمده بدلاً من توثيق أمر غير موجود.
3. تشغيل migrations على قاعدة مؤقتة ثم التحقق من schema.
4. اختبارات unit/domain وAPI contracts.
5. اختبارات auth/RBAC/BOLA وعزل tenant.
6. اختبارات booking concurrency/timezone/state transitions، واختبار over-capacity للحصص إن كانت ضمن الإصدار.
7. اختبارات HTTP/security headers/limits/upload paths.
8. smoke end-to-end للمالك والاستقبال ومقدم الخدمة والعميل.
9. اختبار backup/restore وrollback/forward-fix.
10. تقارير تبعيات وأسرار وثغرات قابلة للمراجعة، مع سياسة لإغلاق الحرجة.

هذه متطلبات تنفيذ مستقبلية في الخطة، وليست تأكيداً أن CI موجود الآن أو أن الاختبارات شُغّلت.

### قبول يدوي production-like

- اختبار رحلة الحجز على هاتف ومتصفح، RTL، بريد sandbox، إلغاء/تعديل، موظف غير مخول، workspace معلق، مزود متوقف، قاعدة بيانات غير متاحة، وإعادة تشغيل الخدمة.
- اختبار تخزين/محو وإخفاء البيانات، صحة الـ audit، وعدم وجود بيانات حقيقية في logs.
- تحديد حدود أداء مستهدفة من حمل متوقع قبل قياس load؛ لا تضع أرقام SLA تخمينية.

## المرحلة 9 — الإطلاق التدريجي

### Go/No-Go

لا يطلق النطاق المحدد حتى تتحقق كلها؛ الموافقة على إصدار واحد لا تعتمد المجالات المؤجلة:

- لا توجد ثغرة P0 أو P1 مفتوحة في المصادقة/التفويض/العزل/التداخل.
- إغلاق واجهات `/api/ops/*` والواجهات القديمة وسجل التطوير أو حمايتها مع اختبارات توضح ذلك.
- مصدر البيانات المعتمد لذلك النطاق ثابت؛ الترحيل والاستعادة موثقان؛ قيم RPO/RTO معتمدة من مالك المنتج.
- جميع اختبارات CI/قبول ما قبل الإطلاق المطلوبة ناجحة على revision محدد، لا smoke فقط.
- مفاتيح production والدومين/TLS والبريد والمراقبة والنسخ والرجوع مهيأة ومراجعة.
- صفحات الخصوصية/الشروط وسياسات الإلغاء والتواصل تتطابق مع الميزات المفعلة ونطاق التشغيل القانوني.
- مالك الإطلاق ومالك الحوادث وخطة التواصل/الإيقاف معروفون.

### التنفيذ

1. إطلاق داخلي بفريق وبيانات اصطناعية، مع feature flags للمجالات التي اجتازت بواباتها فقط.
2. تجربة محدودة مع منشأة متعاونة بعد إغلاق العوائق الأمنية وموافقة الخصوصية؛ راقب مؤشرات الأعطال دون توسيع البيانات المجموعة.
3. توسع تدريجي قابل للإيقاف، مع مراقبة أخطاء API، تعارضات الحجوزات، امتلاء/تجاوز السعة، تأخر الرسائل، زمن الاستجابة، وأخطاء DB.
4. إجراء مراجعة بعد الإطلاق؛ أي حادث خصوصية/تفويض يوقف التوسع حتى تحليل السبب ومعالجته.

| عبارات “وفق المنصات العالمية” قد تُفهم كادعاء تكافؤ أو شهادة | استخدام مراجع منشورة ومعايير كأساس اختبار، لا ادعاء تطابق أو certification | capability matrix وروابط مصدر وتاريخ تحقق، مع حدود التنفيذ الباقية |
| لا توجد قرارات تشغيلية كافية لمركز طلائع | جعل سعة القاعة، أوقات الجمعة، التسجيل للمقرر/الجلسة، الوصي والرسوم أسئلة مملوكة لا افتراضات تنفيذ | إغلاق decision register قبل اعتماد بيانات ومخطط المجال |

## المعايير المرجعية ومقارنة القدرات

هذه المراجع تضبط طريقة التحقق، ولا تعني أن Maw3ed معتمد أو compliant بها. النطاق النهائي يتبع الأسواق والبيانات والمزودين الذين يعتمدهم مالك المنتج.

| المرجع | كيف يستخدم في الخطة | حد الادعاء |
| --- | --- | --- |
| [OWASP ASVS](https://asvs.owasp.org/) و[OWASP API Security Top 10 2023](https://owasp.org/API-Security/editions/2023/en/0x11-t10/) | تحويل المصادقة والتفويض وBOLA والتحقق من المدخلات والجلسات والرفع إلى ضوابط واختبارات قابلة للتتبع | قائمة تحقق واختبارات مشروع؛ ليست شهادة أمنية |
| [NIST SSDF SP 800-218](https://csrc.nist.gov/pubs/sp/800/218/final) | إدخال مراجعة تغيير، حماية الأسرار، اعتماديات آمنة، وأدلة بناء/إصدار ضمن CI | إطار تطوير آمن؛ لا يغني عن تقييم مخاطر المنتج |
| [WCAG 2.2](https://www.w3.org/TR/WCAG22/) مستوى AA كهدف | اختبار كامل لتدفق الحجز ولوحة التشغيل، RTL، keyboard/focus، أسماء عناصر التحكم ورسائل الحالة | لا تعلن المطابقة قبل اختبار الصفحات والعمليات كاملة بشرياً وآلياً |
| [PostgreSQL concurrency control](https://www.postgresql.org/docs/current/mvcc.html) و[explicit locking](https://www.postgresql.org/docs/current/explicit-locking.html) | اختيار القيود/الأقفال والمعاملات حسب الحجز الحصري والسعة واختبار التزامن | التوثيق لا يثبت صحة منطق التطبيق؛ يجب اختبار transaction end-to-end |
| [HL7 FHIR](https://hl7.org/fhir/) | مرجع اختياري إذا اعتمد المنتج تبادل بيانات الرعاية الصحية بين الأنظمة | لا يلزم لنواة المواعيد؛ لا تعلن FHIR conformance دون profile/version واختبارات |
| [PCI Security Standards Council](https://www.pcisecuritystandards.org/) | عند الدفع: تقليل نطاق البيانات عبر hosted checkout/tokenization، وتحديد المسؤولية مع المزود ومختص الدفع | لا تخزن بيانات البطاقة في Maw3ed؛ هذا لا يثبت PCI compliance تلقائياً |
| مراجعة قوانين الخصوصية المحلية وأسواق الإطلاق | تحديد lawful basis/consent/retention/deletion/data residency والوصاية حسب البيانات والسوق | لا تفترض HIPAA أو GDPR أو غيرهما؛ يلزم تحديد السوق ومراجعة قانونية |

تُقارن القدرات المنشورة في [Calendly](https://calendly.com/help/scheduling-faq) و[SimplyBook.me](https://simplybook.me/en/booking-system-features) كفئات عملية: توفر المنطقة الزمنية والـ buffer والمزامنة والإشعارات/التغيير؛ ثم الخدمات والفئات والموظفون والدروس/الأحداث والإيداعات والحزم وقوائم الانتظار. حوّل ما يلائم منتج Maw3ed فقط إلى صفوف في capability matrix مع `مطلوب الآن/لاحق/خارج النطاق` ومالك واختبار؛ لا تستنسخ الميزات أو الأسعار ولا تفترض تفوقاً/تكافؤاً.

## تعريف إنجاز عام لكل مهمة

- متطلب مرتبط بفجوة/رحلة محددة في الوثائق، ومالك قرار واضح.
- تغيير schema/API موثق ومراجع، مع rollback أو خطة forward-fix.
- تحقق خادمي للصلاحيات والبيانات، لا اعتماد على UI.
- اختبارات قبول آلية وسلبية تغطي الخطأ المتوقع، لا النجاح فقط.
- تحديث مستندات التشغيل/الواجهة حتى لا تتقدم الوعود على التنفيذ.
- logs/metrics لا تسجل أسراراً أو بيانات صحية غير لازمة.
- اجتياز قبول ما قبل الإطلاق قبل النشر العام، مع تقرير نتائج وروابط build/revision. لا تعد نتيجة smoke منفردة أو وجود CI دليلاً على قبول كل البوابات.
