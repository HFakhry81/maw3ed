# خط عمل استكمال Maw3ed وتجهيزه للاختبار والإنتاج

**الأساس:** [تقرير الجاهزية](PRODUCTION_READINESS_REPORT.md)، [مواصفات المنتج](PRODUCT_AND_PLATFORM_SPEC.md)، [مقارنة المنصات](REFERENCE_PLATFORM_BENCHMARK.md)، و[خط أساس العمارة والأمان](ARCHITECTURE_AND_SECURITY_BASELINE.md).  
**الحالة عند إعداد الخطة:** مراجعة ساكنة للمستودع؛ لم تُشغّل اختبارات أو بيئة إنتاج.  
**قاعدة التنفيذ:** لا يُفتح الإطلاق العام ولا تُستخدم بيانات مرضى حقيقية حتى اجتياز بوابات الأمن والبيانات والتشغيل أدناه.

## النتيجة المطلوبة

تحويل Maw3ed من نواة حجز وإدارة تعمل جزئياً بمخازن مختلطة إلى منصة قابلة للاختبار والإطلاق المحدود، مع:

1. تفويض خادمي كامل لكل مستأجر ودور.
2. PostgreSQL مصدراً موحداً للبيانات التشغيلية، وحجز ذري لا يسمح بالتداخل.
3. رحلات حجز وزيارة واشتراك ورسائل مكتملة بحدود منتج معلنة.
4. تغطية آلية واختبارية يمكن إعادة تشغيلها، وإعداد staging مماثل للإنتاج.
5. نشر يمكن مراقبته واستعادته والرجوع عنه.

## توزيع التنفيذ حسب الرصيد الحالي

بناءً على الرصيد المتاح في المشروع، يتم تنفيذ العمل على شكل دفعات صغيرة مع استمرار التسجيل والانتقال فقط عند اجتياز كل بوابة. الهدف هو عدم الوقوف بسبب حد الرصيد أو توقف الكتابة أثناء تنفيذ المرحلة.

### المرحلة الحالية
- الحالة: تم توثيق الجاهزية والفجوات، والسياسة واضحة: لا نشر إنتاجي قبل إغلاق P0/P1.
- المكتمل/موثق: تقرير الجاهزية، مواصفات المنتج، خط الأساس المعماري والأمني، خريطة التنفيذ، وصياغة متطلبات المرحلة 0–7.
- قيد التنفيذ/التجهيز: ترتيب الخطة إلى دفعات قابلة للاستئناف، مع كتابة ما تم، ما تبقي، ومخرجات كل مرحلة قبل الانتقال إلى التالية.

### دفعات التنفيذ المقترحة
1. دفعة 1 — القاعدة الآمنة (P0)
   - تم: توثيق المخاطر والمطلوبات، وتحديد المسارات المعرضة.
   - ما تبقي: إغلاق `/api/ops/*` وواجهة التطوير، وإضافة التحقق من عضوية المستخدم وقوة العمل داخل كل طلب.
   - خروج الدفعة: كل مسار خاص يحتاج جلسة + عضوية + RBAC، ولا يوجد endpoint قديم يفلت من هذه السياسة.

2. دفعة 2 — قاعدة البيانات والتزامن (P0)
   - تم: توثيق نموذج PostgreSQL المطلوب، ونسخة قاعدة البيانات والقيود المتوقعة في الخطة.
   - ما تبقي: ترحيل JSON إلى PostgreSQL، فحص التداخل، locks/holds، وإعداد backup/restore وreport mismatch.
   - خروج الدفعة: نجاح اختبارات التزامن، ووجود مصدر بيانات واحد موثّق وقابل للاستعادة.

3. دفعة 3 — رحلات الحجز والزيارة (P1)
   - تم: توثيق state machine، سيناريو الحجز، واستبعاد المنتج غير الناضج.
   - ما تبقي: تنفيذ رحلات الحجز/الإلغاء/إعادة الجدولة/الإشعار داخل الـ API والواجهة.
   - خروج الدفعة: كل تغير في حالة الموعد موثق، والعميل/المدير لا يراها خارج السياق الصحيح.

4. دفعة 4 — الرسائل والدفع/الاشتراك (P1/P2)
   - تم: تعريف نطاق “غير جاهز للإطلاق” إن لم تنجز المزود/التوقيع وwebhook.
   - ما تبقي: sandbox + retry + webhook + opt-out + subscription logic.
   - خروج الدفعة: أي ميزة غير مفعلة تظل مخفية/معلّمة بشكل واضح ولا تُظهر للعميل كخدمة جاهزة.

5. دفعة 5 — التشغيل والخصوصية والمراقبة (P0)
   - تم: تحديد المتطلبات الأساسية من TLS/NGINX/نسخ احتياطي/سجل/مراقبة.
   - ما تبقي: تنفيذها في staging ثم اعتمادها قبل أي إطلاق محدود.
   - خروج الدفعة: جاهزية التشغيل، logs آمن، ونسخ احتياطي لا يستثني قاعدة البيانات.

6. دفعة 6 — بيئة اختبار وقبول (P0)
   - تم: وضع أسس CI/staging واعتبارها مطلباً قبل الإنتاج.
   - ما تبقي: تشغيل smoke + acceptance + security checks على بيئة اصطناعية، وسجل النتائج.
   - خروج الدفعة: قبول staging مع جميع البوابات valdiated وبيانات اصطناعية فقط.

7. دفعة 7 — الإطلاق التدريجي (P0)
   - تم: تحديد شروط الإطلاق والصلاحيات والسحب.
   - ما تبقي: إطلاق داخلي/محدود، جمع المؤشرات، التوسع التدريجي، وقف التوسع عند أي P0/P1.
   - خروج الدفعة: إطلاق محكم مع خطة رجوع واضحة.

### الترتيب التنفيذي الفعلي
- لا تُفتح خطوة جديدة إلا بعد اجتياز معيار الخروج للمرحلة السابقة.
- عند توقف التنفيذ بسبب الرصيد أو الوقت، يستمر العمل من آخر مرحلة مكتملة في السجل الموثق، مع فصل كل دفعة عن الأخرى.
- كل دفعة تُسجل في السجل التوثيقي كـ: ما تم، ما تبقي، ما يثبت أنه مكتمل، ومن هو مالك القرار.

## ترتيب المراحل والبوابات

المراحل مرتبة بحسب الاعتماديات. يمكن إعداد أعمال التوثيق وCI بالتوازي، لكن لا تتجاوز بوابة أمن أو بيانات فاشلة للوصول إلى مستخدمين فعليين.

| المرحلة | الأولوية | النتيجة | لا تنتقل للمرحلة التالية حتى |
|---|---|---|---|
| 0. حصر السطح وخفض التعرض | P0 | قائمة API وقرار واضح لما هو عام/خاص | لا يوجد مسار بيانات تشغيلية مكشوف دون مالك أو قرار |
| 1. المصادقة والعزل والصلاحيات | P0 | وصول خاص يتحقق من الجلسة والعضوية والدور | تمر اختبارات الرفض والوصول المتقاطع |
| 2. مصدر بيانات موحد وحجز ذري | P0 | PostgreSQL مصدر الحقيقة | تنجح اختبارات التزامن والترحيل والاستعادة |
| 3. إكمال رحلات المجال | P1 | حجز/زيارة/تغيير/إشعار متسق | الحالات والسياسات والبيانات مغطاة باختبارات قبول |
| 4. عقود التكامل والاشتراك | P1/P2 حسب إطلاق المنتج | بريد ودفع وتقويم حسب النطاق | كل مزود sandbox/webhook/retry موثق، أو الميزة مخفية بوضوح |
| 5. تشغيل وخصوصية ومراقبة | P0 | تشغيل قابل للدعم والاستجابة | اجتياز قائمة الجاهزية والاستعادة |
| 6. بيئة اختبار وقبول | P0 | staging آمن ببيانات اصطناعية | جميع بوابات CI وQA والاختراق والاستعادة ناجحة |
| 7. إطلاق محدود ثم عام | P0 | إطلاق تدريجي قابل للرجوع | قياسات pilot ضمن الحدود وعدم وجود P0/P1 مفتوح |

## المرحلة 0 — حصر المسارات وخفض التعرض

### العمل

- جرد كل المسارات من `server.js` و`opsRoutes.js` و`platformAdminRoutes.js` حسب HTTP method، مع تصنيفها إلى: عامة، مستخدم مسجل، عضو منشأة، مسؤول منصة، داخلية/محذوفة.
- إيقاف أو حماية عاجلة لـ`/api/ops/*`؛ إذ تقبل مساحة عمل من `x-workspace-id` أو query parameter ولا تتحقق حالياً من عضوية المستخدم.
- إيقاف/حماية الواجهات القديمة `/api/patients`, `/api/appointments`, `/api/dashboard` حتى لا تعتبر مساراتها القديمة استثناءً من سياسة الصلاحيات.
- إيقاف `GET/POST /api/development-events` في الإنتاج أو تقييده بمسؤول مصادق عليه، وإضافة تدوير واحتفاظ للسجل.
- تعطيل التسجيل التلقائي لـ`super_admin` لأول مستخدم في بيئة الإنتاج؛ استبداله بإجراء bootstrap أحادي الاستخدام، موثق، مؤقت ومدقق.
- إعداد قائمة بيانات اصطناعية فقط للاختبار، ومنع نسخ بيانات الإنتاج إلى local/staging دون إخفاء هوية معتمد.

### معيار الخروج

- لكل مسار مالك ونوع وصول معروف.
- جميع المسارات الخاصة ترد `401` دون جلسة، والمسارات العامة تكشف حقولاً مسموحة فقط.
- لا يعود أي endpoint قديم نافذة التفاف حول auth الجديد.

## المرحلة 1 — المصادقة، ملكية المساحة، وRBAC

### العمل

- بناء طبقة مشتركة في الخادم: التحقق من Clerk → استخراج user id → حل workspace من عضوية قاعدة البيانات → التحقق من حالة المستخدم/المساحة → فحص الإذن للعملية.
- اعتبار `x-workspace-id` مجرد اختيار سياق؛ التحقق من membership لكل طلب. يمنع تماماً استخدامه كدليل تفويض.
- تحديد مصفوفة أدوار API: `owner`, `admin`, `manager`, `staff`, `viewer` مع صلاحية مستقلة للتقويم، العملاء، إعدادات الحجز، الأسعار، المصروفات، المستخدمين، والتصدير.
- استبدال صلاحيات الواجهة/localStorage بتفويض على الخادم، مع تقليل الحقول المسموحة لكل دور.
- مراجعة `requireAppUser` ومنطق أول مستخدم، وإجراء bootstrap آمن لدور مالك المنصة دون سباق تسجيل متزامن.
- حماية `/api/ops/*` وكل المسارات القديمة، بما فيها القراءة والإنشاء والتعديل والحذف وعمليات desk.
- منع BOLA: استعلامات وتعديلات appointments/customers/staff/services مشروطة بالمنظمة المحققة، مع عدم كشف وجود كائن في مستأجر آخر.
- توحيد الأخطاء: `401` للهوية الغائبة، `403` للدور غير الكافي، و`404` آمن للكائن العابر للمنشأة؛ لا ترجع stack أو أخطاء قاعدة البيانات.

### اختبارات القبول المطلوبة

- دون جلسة: كل مسارات ops والإدارة القديمة ترفض.
- عضو منشأة A يغير workspace ID إلى B: لا قراءة ولا تعديل ولا تمييز يكشف بيانات B.
- كل دور يمر فقط بالأفعال المسموحة؛ التحقق يشمل التعديل المباشر عبر API، وليس القوائم المخفية فقط.
- user معلق أو workspace موقوف لا ينفذ عمليات تشغيل.
- لا يستطيع مستخدم عادي ترقية نفسه أو تعيين platform role أو استغلال التسجيل المتزامن للحصول على `super_admin`.

## المرحلة 2 — PostgreSQL مصدر الحقيقة وسلامة الحجز

### العمل

- اختيار نموذج موحد: `workspace_id` أو `organization_id`، وتوثيق علاقة workspace/organization ثم إضافة قيود مركبة تضمن أن المريض والموظف والقسم والخدمة والموعد في المستأجر نفسه.
- نقل بيانات `opsStore` وholds وكل إعدادات المنشأة التشغيلية من JSON إلى PostgreSQL. تحديد الجداول، القيود، الفهارس، migration وrollback/forward-fix.
- ترحيل ملفات JSON الموجودة باستخدام أمر dry-run ثم تنفيذ idempotent؛ مقارنة عدد الكيانات والـ IDs والـ slugs والحجوزات بين المصدر والهدف، وتسجيل تقرير تناقض.
- بعد تحقق البيانات، جعل PostgreSQL المصدر الوحيد، وإيقاف الكتابة إلى JSON. الاحتفاظ بنسخة أرشيفية مشفرة فقط ضمن سياسة زمنية محددة.
- نقل rate limits والـ holds إلى خدمة مشتركة/قاعدة بيانات بحيث تعمل عبر workers، وتوثيق سياسة proxy الموثوق لعناوين العميل.
- إنشاء حجز في معاملة واحدة: validate → hold/resource lock → appointment → quota → outbox. كل عمليات retries تستخدم idempotency key.
- فرض منع التداخل حسب `start/end + buffer` لكل مورد، لا تطابق وقت البداية فقط. تضمن قاعدة البيانات أن طلبين متزامنين لا يستطيعان حجز الفترة نفسها.
- فرض تنظيف holds المنتهية وسياسة واضحة لتحريرها عند انتهاء الدفع/الإلغاء.
- تفعيل RLS أو طبقة دفاعية موثقة بعد تحديد دور PostgreSQL، مع التأكد أن دور التطبيق ليس superuser ولا يتجاوز السياسات.

### اختبارات القبول المطلوبة

- طلبان متزامنان للفترة/المورد نفسه: نجاح واحد فقط، والآخر تعارض معروف.
- فترتان متداخلتان جزئياً مع بدايتين مختلفتين: لا يسمح بالتعارض.
- حساب التوفر والحجز النهائي يستخدمان timezone ومدة الخدمة والفاصل والاستثناءات نفسها.
- ترحيل مكرر آمن؛ لا ينشئ نسخاً أو slugs متضاربة، ويصدر تقريراً يمكن مراجعته.
- استعادة backup إلى بيئة معزولة تعيد الجداول والقيود والبيانات اللازمة لتشغيل الحجز.

## المرحلة 3 — إكمال سير العمل والمنتج

### 3.1 الحجز والتقويم

- توحيد state machine من طلب الموعد حتى الإلغاء/الاكتمال/no-show، وتحديد من يستطيع كل انتقال وسبب التغيير.
- دعم ساعات كل مقدم خدمة، إجازات فردية، استراحات متعددة، إغلاق متكرر، مواقع/موارد إذا كانت ضمن الإصدار المستهدف، والمنطقة الزمنية والتوقيت الصيفي.
- إكمال إلغاء/إعادة جدولة العميل برابط موقّع محدود العمر والاستعمال، مع إشعار وتسجيل الحدث.
- تحديد سياسة الموافقة: تأكيد فوري أو pending ثم اعتماد من الاستقبال، وإظهار حالة واضحة للعميل.
- ضمان أن رمز بطاقة الحضور لا يتيح بيانات زائدة، وأنه قابل للإبطال ومحدود المحاولات.

### 3.2 تشغيل المنشأة والبيانات

- إكمال RBAC على موظفي الاستقبال ومقدم الخدمة والمدير والمالك بما يتوافق مع الجدول السابق.
- إضافة pagination/filter/limits للقوائم، وتقليل بيانات المريض إلى ما يلزم لكل شاشة ودور.
- تعريف قيود الاشتراك/usage من `plan_catalog` واشتراك PostgreSQL، مع منع الاعتماد على حدود ذاكرة محلية وحدها.
- وضع سياسة retention، تصدير، حذف، تعديل بيانات العميل، وموافقة رسائل ترويجية منفصلة عن رسائل الخدمة.

### 3.3 التوثيق والواجهة

- تصحيح README وتشغيل التطوير، فهرسة الوثائق، توحيد الأسماء بين booking/customer/patient وworkspace/organization.
- التمييز في واجهة المنتج بين ميزة جاهزة وميزة متوقفة؛ لا تعرض الدفع/المزامنة/التطبيق الأصلي كمتاح إن كان مجرد schema أو WebView.
- تحقيق RTL وإمكانية الوصول واللغة/العملة/timezone عبر رحلة الحجز والإدارة لا في الشاشة الرئيسية فقط.

### معيار الخروج

- سيناريوهات الرحلة من إعداد المنشأة حتى إغلاق الزيارة تعمل من UI وAPI وفق الأدوار.
- لكل تغيير حالة سجل actor/timestamp/source؛ الإشعارات لا تكرر أو تفقد عند إعادة المحاولة.
- واجهات العملاء لا تعرض سجلات أو حقولاً خارج غرضها.

## المرحلة 4 — الرسائل والدفع والتقويم

حدد مبكراً هل هذه ميزات شرط إطلاق أم مرحلة لاحقة. إن كانت ضمن المواصفة، تنفذ كاملة قبل تسويقها.

### الرسائل

- حسم مزود واحد للإنتاج (SendGrid أو SMTP/API آخر)؛ إزالة التناقض بين Gmail/Replit ووثائق VPS.
- تنفيذ transactional outbox، retries بحد أقصى، سجل حالة تسليم، قوالب عربية/إنجليزية، opt-out للرسائل غير التشغيلية، وعدم تسجيل محتوى صحي غير لازم.
- حماية نقاط التحقق من البريد بمعدل لكل بريد/IP/جهاز، صلاحية واستخدام مرة واحدة، ورسائل عامة لا تكشف وجود حساب.

### الدفع والاشتراك

- إبقاء أي checkout معطل معلماً بوضوح حتى اكتمال المزود؛ لا تفعيل اشتراك بناءً على redirect متصفح.
- تنفيذ sandbox أولاً: توقيع webhook، idempotency، مبالغ/عملة موثقة، فشل/إلغاء/استرداد، مطابقة دفتر الاشتراكات، وإشعار المستخدم.
- توثيق آلية التفعيل اليدوي كبديل تشغيلي مؤقت مع فصل موافقة الطالب عن منفذ التفعيل والتدقيق.

### التقويم الخارجي

- اعتماد scopes دنيا، OAuth tokens مشفرة، سياسة تعارض/مصدر الحقيقة، معالجة انتهاء token، وإعادة مزامنة بعد webhook/retry.
- اختبار الحجز في Maw3ed والحجز الخارجي المتزامنين وعدم إنشاء تكرارات عند إعادة الإرسال.

### معيار الخروج

- اختبارات provider sandbox وتوقيع webhook والرسائل الفاشلة/retry ناجحة؛ أو تخفى الميزات غير المنفذة ويذكر نطاق الإصدار ذلك صراحة.

## المرحلة 5 — التشغيل والأمن والخصوصية

- توحيد مدير الحزم وإبقاء lockfile واحد؛ تثبيت إصدار Node LTS في ملف المشروع/CI ووثائق التشغيل.
- فصل الأسرار والبيانات المحلية عن المستودع؛ تدقيق history والمخرجات دون طباعة قيم الأسرار، وتدوير ما يشتبه بتعرضه.
- مراجعة Nginx/TLS: proxy للداخل فقط، forwarded headers موثوقة، HSTS وCSP وnosniff وframe/referrer policy وCORS محدد.
- تحديد body/list limits، معدل طلب موحد، حماية auth/OTP/booking، والحد من التسجيل على القرص.
- عدم كشف رسائل exception للعميل؛ إضافة request ID وstructured logging منقح.
- إضافة readiness منفصل عن liveness، مراقبة DB وqueue/outbox/disk، تنبيهات، نسخة احتياطية مشفرة، سياسة احتفاظ، واختبار استعادة.
- توثيق تصنيف بيانات المريض، الوصول الإداري، طلبات الخصوصية والحذف، إدارة الحوادث، ومن يملك المفاتيح/التصعيد.
- مراجعة تبعيات المشروع وملفات upload ومسارات static على مسارات فعلية قبل إتاحة الإنتاج.

## المرحلة 6 — بناء بيئة اختبار وقبول staging

### تكوين البيئة

- إضافة بيئة `staging` منفصلة عن `local` و`production`: قاعدة بيانات ومفاتيح Clerk ومزودين sandbox ودومين فرعي ونسخ بيانات اصطناعية.
- عدم نسخ `.env.production` أو بيانات حية إلى staging. كل secret له مالك وتاريخ تدوير.
- نشر staging بنفس Node/proxy/DB/migrations وطريقة التشغيل المتوقعة للإنتاج.

### بوابات CI المطلوبة

1. تثبيت نظيف من lockfile وإصدار Node مثبت.
2. فحص تنسيق/تحليل ساكن وبناء frontend/backend.
3. تشغيل migrations على قاعدة مؤقتة ثم التحقق من schema.
4. اختبارات unit/domain وAPI contracts.
5. اختبارات auth/RBAC/BOLA وعزل tenant.
6. اختبارات booking concurrency/timezone/state transitions.
7. اختبارات HTTP/security headers/limits/upload paths.
8. smoke end-to-end للمالك والاستقبال ومقدم الخدمة والعميل.
9. اختبار backup/restore وrollback/forward-fix.
10. تقارير تبعيات وأسرار وثغرات قابلة للمراجعة، مع سياسة لإغلاق الحرجة.

هذه متطلبات تنفيذ مستقبلية في الخطة، وليست تأكيداً أن CI موجود الآن أو أن الاختبارات شُغّلت.

### قبول يدوي في staging

- اختبار رحلة الحجز على هاتف ومتصفح، RTL، بريد sandbox، إلغاء/تعديل، موظف غير مخول، workspace معلق، مزود متوقف، قاعدة بيانات غير متاحة، وإعادة تشغيل worker.
- اختبار تخزين/محو وإخفاء البيانات، صحة الـ audit، وعدم وجود بيانات حقيقية في logs.
- تحديد حدود أداء مستهدفة من حمل متوقع قبل قياس load؛ لا تضع أرقام SLA تخمينية.

## المرحلة 7 — الإطلاق التدريجي

### Go/No-Go

لا يطلق الإنتاج حتى تتحقق كلها:

- لا توجد ثغرة P0 أو P1 مفتوحة في المصادقة/التفويض/العزل/التداخل.
- إغلاق واجهات `/api/ops/*` والواجهات القديمة وسجل التطوير أو حمايتها مع اختبارات توضح ذلك.
- PostgreSQL مصدر الحقيقة؛ ترحيل واختبار استعادة موثق؛ قيم RPO/RTO معتمدة من مالك المنتج.
- جميع اختبارات CI/staging المطلوبة ناجحة، لا smoke فقط.
- مفاتيح production والدومين/TLS والبريد والمراقبة والنسخ والرجوع مهيأة ومراجعة.
- صفحات الخصوصية/الشروط وسياسات الإلغاء والتواصل تتطابق مع الميزات المفعلة ونطاق التشغيل القانوني.
- مالك الإطلاق ومالك الحوادث وخطة التواصل/الإيقاف معروفون.

### التنفيذ

1. إطلاق داخلي بفريق وبيانات اصطناعية.
2. تجربة محدودة مع منشأة متعاونة بعد إغلاق كل العوائق الأمنية؛ جمع مؤشرات أعطال ودعم دون توسيع البيانات المجموعة.
3. توسع تدريجي قابل للإيقاف، مع مراقبة أخطاء API، الحجوزات المتعارضة، تأخر الرسائل، زمن الاستجابة، وأخطاء DB.
4. إجراء مراجعة بعد الإطلاق؛ أي حادث خصوصية/تفويض يوقف التوسع حتى تحليل السبب ومعالجته.

## سجل الأولويات

| الأولوية | العمل |
|---|---|
| P0 — قبل أي نشر عام | auth وtenant membership لكل API، إغلاق مسارات المرضى/المواعيد العامة، حماية dev events، منع الترقية التلقائية لأول مستخدم، حجز ذري، وإيقاف بيانات صحية حقيقية |
| P0 — قبل staging acceptance | مصدر بيانات واحد أو خطة migration محققة، تثبيت runtime/dependencies، CI، backup/restore، logging آمن وproxy/TLS |
| P1 — قبل إطلاق منتج الحجز الكامل | RBAC كامل، حالات وإلغاء/إعادة جدولة، جداول واستثناءات، رسائل موثوقة، حدود خطة متسقة |
| P1/P2 حسب نطاق البيع | الدفع والاشتراك الآلي، تقويم خارجي، SMS/WhatsApp، مواقع متعددة، native mobile |

## تعريف إنجاز عام لكل مهمة

- متطلب مرتبط بفجوة/رحلة محددة في الوثائق، ومالك قرار واضح.
- تغيير schema/API موثق ومراجع، مع rollback أو خطة forward-fix.
- تحقق خادمي للصلاحيات والبيانات، لا اعتماد على UI.
- اختبارات قبول آلية وسلبية تغطي الخطأ المتوقع، لا النجاح فقط.
- تحديث مستندات التشغيل/الواجهة حتى لا تتقدم الوعود على التنفيذ.
- logs/metrics لا تسجل أسراراً أو بيانات صحية غير لازمة.
- اجتياز staging قبل الدمج/النشر للإنتاج، مع تقرير نتائج وروابط build/revision.
