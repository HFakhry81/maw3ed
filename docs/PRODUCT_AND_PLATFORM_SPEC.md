# مواصفات المنتج المرجعية — Maw3ed

**الغرض:** تعريف ما ينبغي أن يكون عليه Maw3ed كمنصة SaaS للحجز وإدارة التشغيل، ثم مقارنة المقصود بالموجود في المستودع. هذه وثيقة هدف منتج قابلة للمراجعة، وليست ادعاءً بأن كل ميزة مدرجة مطبقة.

## 1. تعريف المنتج

Maw3ed منصة متعددة المنشآت لإدارة الخدمات التي تعتمد على موعد: عيادات ومراكز طبية في النطاق الحالي، مع قوالب نشاط قابلة للتوسع. تتيح لكل منشأة إدارة مواردها ومواعيدها وعملائها، وتتيح للعميل الحجز من صفحة عامة، وتوفر لمالك المنصة إدارة الحسابات والخطط.

**القيمة الأساسية:** عرض توفر حقيقي للموظف/المورد، حجز غير متضارب، سير عمل واضح من طلب الموعد إلى الزيارة والإغلاق، مع لوحة تشغيل عربية ودعم تعدد المنشآت.

**حدود الإصدار الأساسي:** جدولة وحجز وإدارة زيارة وسجل تشغيلي. الدفع الإلكتروني، التسويق الآلي، التكاملات، وتطبيق الهاتف الأصلي لا تُعتبر جاهزة ما لم تنفذ وتُختبر وتُوثق.

## 2. الجهات والأدوار

| الجهة | احتياجاتها | صلاحياتها المرجعية |
| --- | --- | --- |
| زائر/مريض | معرفة الخدمات والوقت والسعر وإتمام الحجز أو تعديله | قراءة بيانات عامة محدودة، إنشاء حجز، إدارة حجزه برمز/جلسة آمنة |
| مالك المنشأة | إعداد النشاط والخدمات والموظفين والفوترة والبيانات | تحكم كامل في منشأته، إدارة الدعوات والأدوار والخصوصية |
| مدير/مشرف | تشغيل المنشأة والجدول والموظفين حسب التكليف | صلاحيات مقيدة حسب المنظمة والوظيفة، دون نقل ملكية أو إدارة المنصة |
| استقبال | تقويم، بيانات الحد الأدنى، إنشاء/تعديل الموعد، الوصول والتحصيل | عمليات محددة، لا إدارة اشتراك أو إعدادات أمنية واسعة |
| مقدم الخدمة | جدول ومواعيد وزياراته | مواعيده فقط والحقول التي يحتاجها لتقديم الخدمة |
| مسؤول المنصة | دعم المنشآت وإدارة الخطة والحالة | صلاحية منفصلة ومقسمة بين الدعم والمالية والإدارة العليا، مع سجل تدقيق |
| خدمة آلية | إشعار/تذكير/دفع/تقويم | رموز خدمة محدودة، أسرار محفوظة في مدير أسرار، وتدقيق للعمليات |

## 3. الرحلات الأساسية المطلوبة

### 3.1 إعداد المنشأة

إنشاء الحساب → التحقق من البريد/المصادقة → إنشاء workspace ومنظمة → اختيار النشاط واللغة والمنطقة الزمنية والعملة → دعوة الفريق وتحديد الدور → إنشاء موقع/قسم وخدمات ومقدمي خدمة → ساعات عامة واستثناءات ومهل قبل الحجز → سياسة خصوصية وإلغاء → تفعيل صفحة الحجز.

كل مرحلة يجب أن تكون قابلة للاستئناف، وتُكتب في المستأجر الصحيح، مع سجلات تدقيق للأفعال الإدارية.

### 3.2 الحجز العام

1. يحدد العميل المنشأة والموقع والخدمة.
2. يعرض النظام مقدمي الخدمة الموافقين للخدمة، أو خيار “أي مقدم متاح”.
3. يُحسب التوفر حسب المنطقة الزمنية، ساعات العمل، استراحات الموظف، الإجازات، مدة الخدمة، الفاصل، الموارد والحجوزات القائمة.
4. عند اختيار الوقت يُنشأ hold محدود الزمن ومربوط بالمستأجر والموظف والخدمة والتاريخ.
5. يجمع النظام الحد الأدنى من البيانات، ويعرض السعر والسياسات قبل تأكيد العميل.
6. يُنشأ الموعد مع منع تضارب ذري؛ وتُرسل رسالة تأكيد بعد إتمام commit، مع إعادة محاولة آمنة عبر outbox.
7. يستطيع العميل عرض الموعد أو إلغاءه/إعادة جدولته برمز غير قابل للتخمين قصير الصلاحية ومحدود الاستخدام.

**حالات الموعد المرجعية:** `requested → pending_confirmation → confirmed → checked_in → in_progress → completed` مع مسارات `cancelled`, `no_show`, `reschedule_requested`. يجب حفظ actor والوقت وسبب التغيير، وعدم السماح بانتقالات اعتباطية.

### 3.3 إدارة الجدول والزيارة

- تقويم يوم/أسبوع/شهر مع منطقة زمنية مرئية وفلاتر صلاحيات.
- إنشاء يدوي، نقل وإلغاء، حالة الوصول والزيارة، ملاحظات تشغيلية، وأسعار نهائية عند الحاجة.
- كل تعديل يطبق صلاحية الخادم، يسجل قبل/بعد، ويرسل إشعاراً مناسباً.
- الحالات النهائية لا تُعدل بصمت؛ التصحيح يتم بعملية موثقة.

### 3.4 اشتراك SaaS والمنصة

- قائمة خطط ذات نسخة مؤرخة وحدود/ميزات معروفة.
- الدفع يمر بمزود موثق عبر webhooks موقعة ومعالجة idempotent؛ التفعيل لا يعتمد على redirect المتصفح.
- إدارة الإلغاء والتجديد والفشل والفاتورة والضرائب/العملة وسياسة الاسترداد.
- فريق الدعم لا يستطيع الوصول لمحتوى طبي إلا بتفويض محدد ومسجل.

## 4. نموذج المجال المرجعي

`User` يرتبط بـ `WorkspaceMember(role)`؛ وكل Workspace يحتوي مؤسسة أو أكثر حسب المنتج، ومواقع وأقسام وخدمات ومقدمي خدمة وموارد وساعات/إجازات وعملاء ومواعيد ومدفوعات وإشعارات وتكاملات.

الكيانات المحورية:

| الكيان | الحد الأدنى من البيانات والعلاقات |
| --- | --- |
| Workspace | المالك، الحالة، slug، الخطة، الإعدادات، المنطقة الزمنية، العملة |
| Membership | user + workspace + role + status + invitation metadata |
| Service | المدة، buffer، السعر/النطاق، سياسة الحجز، مقدمون مؤهلون |
| Provider/Resource | جدول أسبوعي، استثناءات، إجازات، موقع، سعة |
| Customer/Patient | بيانات اتصال لازمة، تفضيلات/موافقات، مرجع مستأجر ثابت |
| Appointment | tenant + customer + service + provider/resource + فترة زمنية + حالة + الأسعار |
| Hold | الفترة/المورد/المستأجر + انتهاء صلاحية + مفتاح idempotency |
| Payment/Invoice | مبلغ وعملة وحالة ومصدر خارجي، دون تخزين بيانات بطاقة حساسة |
| Notification/Outbox | قالب، مستلم، حالة إرسال، retry، correlation id |
| AuditEvent | فاعل، tenant، فعل، target، قبل/بعد منقح، توقيت ومصدر |

قواعد سلامة: مفاتيح أجنبية مركبة تضمن وحدة المنظمة؛ مواعيد غير متداخلة حسب الموارد؛ uniqueness للـ slugs داخل النطاق المطلوب؛ أرشفة/حذف وفق سياسة احتفاظ، لا حذف عشوائي لسجلات مالية.

## 5. المتطلبات غير الوظيفية المستهدفة

- **الأمن:** المصادقة للخادم، least privilege، tenant isolation افتراضي، تقليل بيانات الصحة، جلسات آمنة، HTTPS، حماية CSRF حيث تلزم، حدود لكل API، وعدم الوثوق بأي tenant ID يرسله العميل.
- **الاعتمادية:** نسخ احتياطي تلقائي مشفر، اختبار استعادة، تعريف RPO/RTO، health/readiness، تنبيه فشل الإرسال والترحيل، وخطة رجوع.
- **الجدولة:** مرجع زمني موحد UTC مع timezone للعرض، معالجة DST، منع تداخل ذري، والـ idempotency لطلبات الإنشاء.
- **الخصوصية:** جمع الحد الأدنى، تقييد وصول الموظف، إدارة موافقات الاتصال، سجل وصول إداري، retention/delete/export policy، وبيان نطاق التعامل مع البيانات الصحية حسب سوق التشغيل.
- **الأداء:** pagination وفلاتر مفهرسة، حدود صريحة لحجم الطلب وقوائم الاستجابة، load shedding، وrate limits متعددة النسخ.
- **التشغيل:** lockfile واحد، إصدار Node مثبت، CI migrations/build/security checks، secrets خارج Git، سجل structured لا يحوي بيانات حساسة، وإجراء incident response.
- **إمكانية الوصول والتدويل:** عربي RTL كامل، لغة ثانية متسقة، صيغ التاريخ/الرقم/العملة حسب locale والمنطقة الزمنية، استخدام لوحة مفاتيح وقارئ شاشة.

## 6. المقارنة مع التنفيذ الحالي

| المجال | موجود أو موصوف في Maw3ed | الفجوة المرجعية |
| --- | --- | --- |
| البوابة العامة | مسار حجز واختيار خدمة/موظف/وقت وحفظ الطلب | إلغاء/إعادة جدولة ذاتية، موافقات، intake forms وسياسات واضحة تحتاج اكتمالاً |
| الساعات | ساعات وجداول وإغلاق يوم محدد وفق الوثائق | استثناءات متقدمة، تعدد الاستراحات، موارد/سعة، حالات المنطقة الزمنية/DST تحتاج إثباتاً |
| منع التضارب | hold وقواعد 409؛ بعض قيود DB للحظة البداية | منع ذري لتداخل فترات/المدة/buffer عبر كل العمال والنسخ |
| عمليات المنشأة | تقويم/عملاء/طاقم/خدمات/مكتب زيارة ومصروفات | هذه الواجهات غير محمية حالياً بتفويض خادم، وهي مانع إنتاج |
| تعدد المستأجرين | workspaces/memberships في DB وملفات JSON مفصولة | مصدر التخزين غير موحد، ID يأتي من العميل في ops، ولا توجد RLS/سياسات دفاعية |
| RBAC | أدوار إدارة منصة موجودة، أدوار أعضاء مسجلة في schema | أدوار تشغيل العيادة لا تنفذ على API كما ينبغي |
| الرسائل | بريد/Outbox حسب بعض الوثائق | تناقض Gmail/Replit مع إنتاج VPS/SendGrid؛ retries وإثبات تشغيل غير محسومين |
| الدفع | جداول سجل مالي وخطة؛ تفعيل يدوي | checkout الآلي معطل، لا تسوية مزود أو webhooks موثقة |
| الهاتف | غلاف WebView | لا يساوي تطبيقاً أصلياً أو وظيفة تشغيل دون اتصال |
| التشغيل | VPS/Nginx/systemd أو PM2 موصوف | لا دليل CI/CD، مراقبة، استعادة، rollback أو اختبارات بيئة إنتاج |

## 7. تعريف إنجاز الإصدار الأول

يُعد الإصدار الأول قابلاً لإطلاق محدود فقط عندما: (أ) كل API داخلي يطبق مصادقة وعضوية ودور خادمي، (ب) لا يمكن لمستخدم تبديل tenant ID للوصول لمستأجر آخر، (ج) مصدر بيانات واحد متين مع backup/restore مجرب، (د) الحجز الذري يمنع تداخل الخدمة والموارد، (هـ) البريد والـ domain وTLS والمراقبة وخطة الرجوع موثقة ومجربة، و(و) تحقق اختبارات الوصول والمزامنة والترحيل والاستعادة من نتائج نجاح قابلة للمراجعة.
